# AdminAX 채팅 파이프라인 테스트 시나리오

현재 소스코드 및 Docker Compose 구조를 분석한 결과, **프론트엔드 UI부터 백엔드 API, 그리고 Python LLM 워커까지 전체 파이프라인이 로컬 테스트 가능한 상태**로 구성되어 있습니다. 

## 1. 사전 점검 및 서비스 기동
테스트를 시작하기 전에 최신 코드가 반영되어 모든 컨테이너가 정상적으로 실행되는지 점검해야 합니다.

1. **빌드 및 재기동**
   터미널에서 아래 명령어를 통해 최신 코드로 엔진과 UI 컨테이너들을 갱신 및 재기동합니다.
   ```bash
   docker compose up -d --build
   ```
2. **AI 워커 구동 확인**
   LLM 응답을 담당하는 워커가 잘 떠있는지 로그를 확인합니다.
   ```bash
   docker compose logs -f chat-worker
   ```
   *로그에 `[*] AdminAX Chat Worker listening on adminax:chat:stream...` 및 모델 로딩 완료 메시지가 떠야 정상입니다.*

## 2. 웹페이지 접근
- **접근 주소**: 브라우저에서 서버의 IP 주소 또는 로컬호스트로 접속합니다.
  - 보통 `http://localhost` 또는 `http://<서버IP>` (Nginx가 `.env`의 `GATEWAY_PORT=80`을 통해 80번 포트를 리스닝 중이며, `/` 경로를 `chat-ui`로 포워딩합니다.)

## 3. 채팅 테스트 시나리오 수행

### 시나리오 A: 일반적인 질의응답 (문서 없이 LLM 단독 대화)
1. 화면 하단의 텍스트 입력창에 `안녕하세요. 당신은 누구인가요?` 라고 입력합니다.
2. [전송] 버튼이나 Enter 키를 누릅니다.
3. **기대 결과**:
   - 메시지 전송 직후 버튼이 네모 모양(Stop)으로 변하며 `답변을 생성 중입니다...`라는 SSE 상태 메시지가 잠깐 뜹니다.
   - 워커가 Redis 큐를 읽어 Qwen 모델로 응답을 생성하고, 서버를 거쳐 UI 채팅창에 타이핑 효과로 텍스트가 렌더링 됩니다.

### 시나리오 B: 지식 재료(문서) 첨부 후 RAG 테스트 
1. 채팅창에 테스트용 문서(예: 짧은 텍스트 파일 `.txt` 이나 `.hwp`, `.pdf`)를 **드래그 앤 드롭** 하거나 클릭하여 첨부합니다.
2. 첨부 직후 입력창 위에 파란색 뱃지로 **파일 이름과 함께 "준비 중..."** (이후 '분석 중' -> '정규화 완료') 상태가 표시되는 것을 확인합니다.
   - *이때 프론트엔드가 `/api/norm/subscribe/{taskId}` (SSE)로 백엔드의 Ingestion Service와 통신하며 프로그레스 바를 그려줍니다.*
3. 정규화가 완료되면 텍스트 입력란에 아무 내용도 적지 않고 **빈칸인 상태에서 [전송]**을 누릅니다. 
   - (이전에 수정해둔 로직에 의해 자동으로 `"첨부된 문서들의 핵심 요약을 제공해줘."` 라는 프롬프트가 발송됩니다.)
4. **기대 결과**:
   - `지식 재료를 모으는 중입니다... (정규화 대기 중)` 상태가 표시된 뒤 `답변을 생성 중입니다...` 로 넘어갑니다.
   - LLM이 첨부한 내용의 Context를 바탕으로 요약 및 답변을 생성하여 출력합니다.

## 4. 트러블슈팅(Troubleshooting) 시 참고
* "Unexpected end of JSON input" 등 SSE 파싱 오류가 발생하면 페이지를 갱신(역할 F5)하고 시도해 봅니다. (방금 패치로 해결되었어야 정상입니다.)
* LLM 생성 응답이 너무 늦어질 경우 (Qwen 모델 크기에 따라 GPU/CPU 파워 소모가 큽니다) `ChatController`에서 10분으로 늘린 Timeout 내에 오는지 살펴봅니다. (워커의 최대 생성 토큰 `AI_MAX_TOKENS`가 1024로 잡혀 있어 시간이 걸릴 수 있습니다.)
